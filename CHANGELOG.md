## 2.8.13 — Fix: Broadcasting a Placement to Other Documents No Longer Overwrites a Second Signature Instance

- Fixed a real bug reported as "masih error, ttd malah tertimpah di posisi yg sama" (still broken, the signatures end up overwritten at the same position) — this surfaced even after 2.8.12, because it lived in a different, older code path than the one 2.8.12 fixed. 2.8.12 fixed the new "Copy every signature on this page to" feature; this fix addresses the same underlying class of bug in the much older "Apply to selected PDFs" checkbox + Save Placement flow, which broadcasts whichever signature box you're currently positioning to every other selected document.
- Root cause: when a page has two instances of the *same* signature (e.g. one signer stamped in two spots), dragging the first instance with "Apply to selected PDFs" checked correctly created a placement on every target document. But dragging the *second* instance afterward and broadcasting it again reused the exact same target row the first broadcast had just created — matched only by signature+page, with no idea there were two separate instances involved — so the second instance's position silently overwrote the first one's on every target document. The source document kept both instances at their correct, distinct positions the whole time; only the broadcast copies collapsed into one.
- Fix: a broadcast placement is now matched to its target by *ordinal position* among same-signature instances on that page, not just by signature+page. The 1st instance placed on the source page is matched to the target's 1st instance of that signature on that page (updating it if one already exists there, exactly as before), the 2nd instance is matched to the target's 2nd, and so on — adding a new one on the target whenever it doesn't have that many yet, instead of colliding with an unrelated instance. A target whose matched instance is already locked is left untouched and reported back as needing manual adjustment, rather than aborting the broadcast for every other selected document.
- Verified end-to-end in an isolated test environment via full browser-driven interaction (not just direct API calls): placed one signature instance on a source document, checked "Apply to selected PDFs" against a second document, and dragged it — confirmed the target received exactly one placement at the matching position. Added a second instance of the *same* signature on the source page via "+ Add signature," dragged it to a distinct position with broadcast still on — confirmed the target document ended up with two distinct placements at two distinct positions (previously: one placement, overwritten to the second position). Re-dragged the first instance again and confirmed the broadcast is idempotent (still exactly two placements on the target, the matching one updated in place, no duplicate created). Locked the target's matched instance directly and re-broadcast a reposition of the source instance — confirmed the request still succeeds for the request as a whole (HTTP 200), the locked target instance is left completely unchanged, and it's reported back as needing adjustment. Ran the full sign flow afterward on the source document (two placements, one deliberately left unconfirmed) — confirmed signing is correctly refused until it's confirmed, and once confirmed, the resulting signed PDF was inspected directly and contains two separate signature images at two clearly distinct, non-overlapping positions on the page. Real production database confirmed byte-identical (md5) before and after; all synthetic test files, documents, signatures, and the isolated app copy were deleted after verification.
- CSS/JS cache key bumped to 2.8.13.

## 2.8.12 — Fix: Copying a Page Range Now Handles Two Instances of the Same Signature Correctly

- Fixed a real bug in the "Copy every signature on this page to" feature added in 2.8.11: it worked correctly for two *different* signatures on the same page, but not for two *instances of the same signature* at different positions on one page (e.g. one signer stamped twice — once for an upper form block, once for a lower one, exactly as reported: "posisi ttd 1 ada di atas, ttd 2 ada dibawah"). The server tracked "does the target page already have this signature" keyed only by signature ID, so the moment the first instance was copied to a target page, the second instance of that same signature was silently treated as a duplicate and skipped for every target page — the position and count were not actually preserved for this specific, very common case (the same person signing more than one place on a page).
- Fix: the server now tracks "already present" per exact signature **and position** (not signature alone), so two instances of the same signature at different spots are each copied independently to every target page, while re-running the copy is still fully idempotent (an exact signature+position combination that's already there is still correctly skipped, never duplicated).
- Verified end-to-end in an isolated test environment: reproduced the exact bug first (2 instances of one signature, positions ny=0.20 and ny=0.70, copying to 7 pages came back "copied: 7, skipped: 7" — only the first instance survived on each target page); confirmed the fix resolves it ("copied: 14, skipped: 0", both positions present on all 7 target pages); confirmed idempotency still holds on a second identical run; confirmed a mixed case (2 instances of one signature + 1 instance of a second, different signature on the same source page) correctly produces all 3 placements, each at its own exact position, on every target page; confirmed the full "Sign Selected PDFs" flow still signs successfully afterward. Real production database confirmed byte-identical (md5) before and after; all synthetic test files, documents, signatures, and the isolated app copy were deleted after verification.

## 2.8.11 — Fix: Applying a Page Range Now Carries Every Signature on the Page, Not Just One

- Fixed a real gap reported as: "di halaman 3 ada 2 ttd, lalu saya ingin aplikasikan ke halaman 4-10, itu tidak berubah, hanya 1 ttd saja yg diam" — page 3 has 2 signatures, applying to pages 4-10 only carried one of them; the other stayed behind on page 3. Root cause: the existing page grid ("Position on PDF" step, click a page to toggle it / Shift-click for a range) has always operated on whichever ONE signature is currently selected in the signature dropdown — it was never designed to know about a second, different signature also placed on the same page, so a range applied through it only ever replicated the active signature and silently left any other signature on the source page exactly where it was.
- New control added directly under the page grid: "Copy every signature on this page to" — a page range input (e.g. `4-10`) plus a Copy button. Unlike the page grid, this looks at every placement actually on the page you're currently viewing and replicates all of them, each at its own already-saved position, to every page you list — so two (or more) different signatures on one page move together in a single action. Purely additive: a target page that already has a placement for a given signature is left completely untouched for that signature (never overwritten, resized, or duplicated), and nothing is ever removed by this action.
- New endpoint `POST /api/signing/apply-page-range` (`{attendance_id, source_page, target_pages}`) implements the copy server-side; returns exactly which placements were copied (with their new ids) and how many were skipped because the target already had that signature.
- The existing page grid and its Shift-click range-toggle are completely unchanged — still the right tool for adding or removing one specific signature across a range; the new control is for the separate, previously-unsupported case of carrying a page's full signature set forward together.
- Verified end-to-end in an isolated test environment: seeded a 10-page document with two different signatures placed on page 3 (matching the exact reported layout) and applied the new page range to pages 4-10; confirmed all 14 expected placements (2 signatures × 7 target pages) were created with the correct signature and exact source position, confirmed re-running the same copy is a no-op (everything correctly reported as already-present/skipped, nothing duplicated), confirmed an empty source page, an out-of-range target page, and an empty or source-only target list are all correctly refused with a clear error, and confirmed the full "Sign Selected PDFs" flow still signs successfully with the resulting 16 placements spread across 8 pages. In the browser: filled in the new control on page 3, confirmed the center banner reported "14 signature(s) copied," and confirmed navigating to a target page (page 5) shows both signatures rendered there, not just one. Real production database confirmed byte-identical (md5) before and after; all synthetic test files, documents, signatures, and the isolated app copy were deleted after verification.

## 2.8.10 — Fix: Dragging No Longer Locks a Signature Box Against Itself

- Fixed a regression introduced in 2.8.9: dragging a signature box (the plain, single-placement case — not the "+ Add signature" extra-instance case) auto-saved as usual, but the box then immediately became locked and could not be dragged again without first unchecking a box that was never explicitly checked. Reported as "ketika sign saya geser langsung auto save tidak bisa di geser lagi" — auto-save itself was fine, but the box needed to stay flexible afterward.
- Root cause: `confirmed` (whether a placement counts toward signing — see 2.8.9) and "locked against dragging" were driven off the same flag. The ordinary single-signature flow has always defaulted to `confirmed=1` from its very first save, purely so it stays sign-ready without requiring a manual check — but the frontend also read that same default as "the user locked this," so the first autosave after any drag froze the box against itself.
- Fix: split the two into separate, independent flags. New column `attendance_signature_placements.locked` (default: unlocked), added via the existing additive-migration pattern. `confirmed` keeps its 2.8.9 meaning unchanged — it still gates signing, and the ordinary single-placement flow still defaults to confirmed automatically. `locked` is purely a human-driven flag: it starts false for every placement, old and new, confirmed or not, and only ever becomes true through the confirm checkbox itself (`/api/signing/placement/confirm`, which now sets confirmed and locked together — checking locks and confirms in one step; unchecking frees the box to be dragged again but also pulls it back out of signing until it's reviewed and re-checked). A plain drag/resize autosave never touches `locked`, so a box can now be repositioned any number of times in a row without ever locking itself, exactly as before 2.8.9 — while the confirm-and-lock checkbox from 2.8.9, and the sign-time refusal for a genuinely unconfirmed extra instance, both work exactly as designed.
- The server now also refuses (400, "This signature placement is locked -- uncheck it before moving it") an attempt to reposition a placement that is explicitly locked, addressed by its exact `placement_id` — a defense-in-depth check behind the frontend's own drag guard.
- Verified end-to-end in an isolated test environment: (1) simulated a database carrying the 2.8.9 schema (a `confirmed` column but no `locked` column, with a real legacy placement row) and confirmed the additive migration runs cleanly and the legacy row comes out `confirmed=1, locked=0` — signable and fully draggable, matching intent; (2) via direct API calls, repositioned the same placement twice in a row and confirmed both saves returned `locked:false`, confirmed an explicit `/api/signing/placement/confirm` call locks it (`confirmed:true, locked:true`) and that a further reposition attempt on it is correctly refused with the new 400 error, confirmed unchecking frees it (`confirmed:false, locked:false`) and allows repositioning again, and confirmed a fresh "+ Add signature" extra instance still starts `confirmed:false, locked:false` and can be dragged before it's ever checked; re-ran the full sign flow (refused while any placement is unconfirmed, succeeds once every placement is confirmed) and confirmed it is unaffected; (3) in the browser: dragged a signature box twice in immediate succession and confirmed the second drag moved it just as freely as the first (the exact reported scenario), confirmed checking the confirm box adds the locked visual state and genuinely prevents a subsequent drag, and confirmed unchecking it removes the locked state and restores dragging. Real production database confirmed byte-identical (md5) before and after; all synthetic test files, documents, and the isolated app copy were deleted after verification.
- CSS/JS cache key bumped to 2.8.10.

## 2.8.8 — Unlimited Signature Instances Per Page

- Removed the cap on "+ Add signature": it no longer refuses to add a signature just because every registered signature already has a placement on the current page. The picker now always lists every registered signature, including ones already placed here, and choosing one always starts a brand-new placement — so the same signer can be stamped in more than one spot on a page (e.g. two separate approval boxes for the same person), not just once.
- This required a real schema change: `attendance_signature_placements` previously allowed only one placement per (document, signature, page) via a `UNIQUE` constraint, which is exactly what made "all signatures are already placed on this page" happen once every registered signature had been used once — there was no way to add a second copy of the same signature. That constraint is now removed, and a page can hold any number of placements for the same signature. Existing databases are migrated automatically and in place the first time the app starts on this version (see Database migration below); newly created databases never had the constraint to begin with.
- The "Signatures on this page" chip row now shows one chip per individual placement instead of one per distinct signature — if the same signer is placed twice, two chips with that name appear, each independently clickable, draggable, and removable. Clicking a chip brings back exactly that instance's position for repositioning; its × (or the "Remove from this page" button, for whichever instance is currently active) deletes only that one instance, leaving any others exactly where they are.
- A newly added instance's box starts at a small offset from previous ones already on the page (rather than exactly on top), so it's obvious there's something new to drag into place.
- No change to the auto-save-on-drag, the "Remove from this page" button, the drag/resize center-screen confirmation, the auto-detect panel, or the end-of-batch redirect to Attendance — all from 2.8.7 and unaffected by this release.
- Backend: `/api/signing/placement` accepts an optional `placement_id` (update one exact instance) and `new_instance` (always insert a fresh row instead of reusing an existing one for the same signature+page); neither flag is required for the ordinary single-instance case, which behaves exactly as before. `/api/signing/placement/remove` accepts an optional `placement_id` for precise single-instance deletion. Broadcasting a placement to other selected PDFs ("Apply to selected PDFs"), "Remember this position" templates, auto-detect, and "suggest position" all continue to operate on a single canonical instance per signature/page/document, unaffected by this change — the new multi-instance capability only applies to the one document currently open in the workspace.
- Database migration: on startup, if `attendance_signature_placements` still carries the old `UNIQUE(attendance_id,signature_id,page)` constraint, the table is rebuilt without it (same columns, same data, same row ids — nothing is dropped or renumbered) before the rest of schema setup runs. This is safe to run multiple times: once the constraint is gone, later startups see nothing to migrate and skip it.
- Verified end-to-end in an isolated test environment: (1) simulated an existing pre-2.8.8 database (old constrained schema, real foreign-key targets, a legacy placement row) and confirmed the startup migration removes the constraint while preserving the existing row's id and data untouched, that a duplicate (same document/signature/page) insert now succeeds where it previously would have violated the constraint, and that running the migration a second time is a no-op; (2) with only two registered signatures, placed the same signature twice on one page via drag and via "+ Add signature" picking the already-placed signature again, confirmed no blocking toast appeared and two independent chips showed up with different underlying ids; (3) clicked between the two chips and dragged each, confirming only the actively selected instance's row changed and the other was untouched; (4) removed one instance via "Remove from this page" and confirmed only that instance disappeared, the other remained, and the signed output PDF contained exactly one stamped image (not two, not zero); (5) re-confirmed the 2.8.6 resurrection-guard fix still holds in the new model — adding a signature via "+ Add signature" and signing without dragging it correctly excludes that never-touched instance from the signed output. Real production database confirmed byte-identical (md5) before and after; all synthetic test files, signatures, documents, and the isolated app copy were deleted after verification.

Clicking "Change" reopens the full picker; selecting a signature (or re-selecting the same one) collapses it again.
- Steps 2 (position) and 3 (apply/save) are merged into a single working area: the page grid, the "Pages to sign" field, the Apply/Save controls, and a new mini Prev/Next page navigator (so you can step through pages without scrolling up to the main PDF toolbar) all live together in one place instead of being split across two separate columns.

Success notes fade out automatically after a few seconds; error messages (e.g. an invalid page number) stay visible until the next action, so a mistake is never missed by fading too fast.

- The panel's subtitle text was updated to describe the new top-to-bottom flow instead of the old "four steps left to right" wording.

## 2.8.2 — Clickable Page Grid for Selective Signing

## 2.8.1 — Selective Page Signing

- Signing workspace: a document no longer has to be signed on every page. A new "Pages to sign" field (in the Position on PDF step) accepts a page list or range — e.g. `1,3,5` or `1-3` — and Apply keeps only those pages' placements, removing any others in one action. This is useful when auto-detect (or a batch apply) placed a signature on more pages of a document than actually need it.
- Signing workspace: the currently open document also shows a small chip for each page that currently has a saved placement (e.g. "Page 1 ×", "Page 3 ×"); clicking a chip's × removes just that one page's placement. The "Pages to sign" field is pre-filled with the document's current placement pages whenever it's opened, so it always reflects reality and Apply can be used to fine-tune from there.
- The document queue's "Placed" indicator and the auto-detect "Ready"/"Needs review" badges now update live as placements are added or removed this way (previously they only reflected the state at page load), and a document whose last placement is removed is automatically unchecked from the signing batch.
- New read-only-safe endpoints backing this: `POST /api/signing/prune-pages` (keep only the given pages, delete the rest) and `POST /api/signing/placement/remove` (delete one page's placement). Both only ever delete rows from the existing `attendance_signature_placements` table — no schema change, and the final `/api/signing/sign` step is unchanged: it still only stamps whatever placements remain, so removing a page's placement is equivalent to simply never signing that page.
- Verified end-to-end in an isolated test environment: placed a signature on all pages of a synthetic 5-page PDF, pruned down to pages 1/3/5, removed page 3 individually, re-added it, then signed — confirmed by inspecting the signed output that only pages 1, 3, and 5 actually received the signature image while pages 2 and 4 were left untouched. Also verified live in the browser that removing a chip or applying a page range updates the on-screen chips, the "Pages to sign" field, and the queue's "Placed" badge without a page reload.
- CSS/JS cache key bumped to 2.8.1.

## 2.8.0 — Dashboard Widgets, Bottom Page Navigation, Auto-Detect Signature Placement

- Dashboard: the weekly trend sparkline is now a proper bar chart (per-day bars with hover tooltips showing the exact value) instead of a thin single-line polyline, using the same trend data the dashboard already computed.
- Dashboard: added three new widgets — "Team Activity" (who uploaded or signed documents in the last 7 days, from the existing audit log), "Waiting Too Long" (open attendance documents that have sat in Uploaded/Checking/Ready to Sign for more than 3 days, oldest first, linking straight to each document), and "Open Tickets by Priority" (a Critical/High/Medium/Low breakdown of tickets that are still open). All three are read-only summaries of existing data — no new tables, no changes to how attendance or ticket records are created or edited.
- Signing workspace: the Prev/Next page buttons are now duplicated at the bottom of the PDF preview pane (in addition to the existing pair in the top toolbar), so after dragging a signature into position at high zoom you no longer need to scroll back to the top of the page just to advance — both pairs stay in sync and share the same keyboard/zoom-aware logic.
- Signing workspace: added an "Auto-detect" step. Enter one or more keywords that label the signature spot in your documents (defaults to "Menyetujui, Mengetahui Atasan Langsung", matching the real approval labels used in CGK3 attendance/overtime forms), then Scan. For every queued, unsigned document the system searches the PDF's actual text layer for each keyword and only accepts a page where a keyword matches exactly once (a page where a label appears more than once — e.g. an overtime form with two separate approval sections — is left for manual placement rather than guessed); the signature box position and size are derived from the blank space directly below the matched label, bounded by the next line of text and any neighboring column, so it lands in the same place a person would drag it. Documents where every page was confidently matched are placed and auto-checked in the queue; anything with an unmatched or ambiguous page is flagged "needs review" and left unchecked for manual handling — nothing is ever placed or signed without a match. This still ends at your own "Sign Selected PDFs" confirmation step; auto-detect only removes the manual dragging, not the final review-and-confirm click.
- Verified end-to-end (in an isolated test copy of the app, never the production database) against a real 20-page attendance/overtime PDF: correctly placed signatures on the 3 pages with an unambiguous label, correctly deferred the 15 pages with a duplicated label to manual review, and correctly left the 2 unsigned scanned-attachment pages (no text layer) untouched — confirmed by rendering the signed output back to an image and checking the signature lands in the intended blank space.
- No changes to the attendance batch-signing logic's core placement storage, delete/audit safety rules, or permission checks — auto-detect only pre-fills the same `/api/signing/placement` call a manual drag already makes.
- CSS/JS cache key bumped to 2.8.0.

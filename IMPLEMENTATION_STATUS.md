# Implementation Status — 2.8.13

Fix release: broadcasting a placement to other documents via the "Apply to selected PDFs" checkbox + Save Placement flow no longer collapses two instances of the same signature into one. This is a different, older code path than the one 2.8.12 fixed (2.8.12 fixed the newer "Copy every signature on this page to" control) — the same underlying class of bug (matching "already present" by signature+page alone, with no concept of separate instances) lived in both places independently, and this release fixes the second occurrence.

## New this release (2.8.13)

- `main.py`: `signing_placement()`'s broadcast loop (the `apply_ids` handling) now matches each target document's placement by **ordinal position** among same-signature instances on that page, instead of blindly reusing whichever row is found first. Before saving to a broadcast target, the source placement's own ordinal (1st, 2nd, ... instance of this signature on this page, by creation order) is computed, and the matching ordinal instance is looked up on the target document: if it exists, it's updated (unchanged behavior for the ordinary single-instance case); if the target has fewer instances than that ordinal, a new one is inserted instead of colliding with an existing lower-ordinal instance that belongs to a different source placement.
- `main.py`: a target whose matched instance is locked is now caught and reported back in the existing `mismatched`/`mismatched_names` response fields (the same "needs manual adjustment" list used for a page-layout mismatch) rather than raising an unhandled error that would abort the broadcast for every other selected document.
- No schema change, no frontend change, no i18n keys added — the fix is entirely inside this one endpoint's broadcast bookkeeping; the request/response shape is unchanged (broadcast targets already returned via the existing `applied`/`mismatched` fields).

## New in 2.8.12 (carried forward, unchanged this release)

Fix release: the "Copy every signature on this page to" feature from 2.8.11 now correctly handles two instances of the SAME signature at different positions on one page (e.g. one person signing both an upper and a lower form block on the same page) -- previously the second instance was silently dropped from every target page because the server treated "signature already on the target page" as true the moment the first instance was copied there. See "New in 2.8.12" further below for full detail.

## New in 2.8.12

- `main.py`: `signing_apply_page_range()`'s de-duplication key changed from `(signature_id, page)` to `(signature_id, page, nx, ny, nw, nh)` (position rounded to 4 decimals). The old key meant a second instance of the same signature on the source page -- at a different position -- was treated as "already covered" the instant the first instance landed on a target page, so it was skipped for every target page: the count (2) was never actually preserved for this case, only for two *different* signatures. The new key only treats a source placement as already-present on a target page when that EXACT signature+position combination is already there, so two (or more) distinct-position instances of one signature are each copied independently, while re-running the copy is still fully idempotent.
- No schema change, no frontend change -- the bug and its fix are entirely inside this one endpoint's internal bookkeeping; the request/response shape is unchanged.

## New in 2.8.11 (carried forward, unchanged this release)

Fix release: applying a page range now carries every signature placed on the source page, not just whichever one happens to be selected in the dropdown. The existing page grid (click a page / Shift-click a range) has always operated on a single active signature; a new, separate "copy this page to other pages" control replicates every placement on the current page together in one action. See "New in 2.8.11" further below for full detail.

## New in 2.8.11

- `main.py`: new endpoint `POST /api/signing/apply-page-range` — `{attendance_id, source_page, target_pages}`. Reads every placement row on `source_page`, and for each `target_page` × each source placement, inserts a new placement at the source's exact `(nx,ny,nw,nh)` for that same `signature_id` UNLESS the target page already has a placement for that signature (skipped, never overwritten/duplicated). Validates `source_page` and every `target_page` against the document's real page count, requires at least one target page other than the source, and requires the source page to have at least one placement to copy. Returns the full list of copied rows (with real ids) plus a skipped count, so the frontend can update its cache with accurate data rather than guessing.
- `attendance_signing.html`: new control directly under the page grid — a text input (`#pageCopyInput`, same page-range syntax as the existing "Pages to sign" field, e.g. `4-10`) plus a "Copy" button (`#pageCopyApply`), with a one-line hint clarifying it copies ALL of the current page's signatures, not one at a time. Reuses the existing `.page-scope-row`/`.page-scope-label` CSS classes — no new styling needed.
- `app.js`: new `#pageCopyApply` click handler. Checks the current page actually has at least one placement to copy (`pageInstances().length`) before calling the server; on success, merges the server's returned `copied` rows (each with a real id) directly into the cached placement list for the document, then re-renders the page grid/instance boxes and shows a "N signature(s) copied to page(s) …" (or "nothing new to copy" if everything was already present) center notice.
- No schema change, no change to `confirmed`/`locked` semantics from 2.8.10, no change to the existing page grid's own click/Shift-click behavior — this is a purely additive new capability alongside it.
- New i18n keys (both languages): `sign.controls.copy_page_label`, `sign.controls.copy_page_ph`, `sign.controls.copy_page_apply`, `sign.controls.copy_page_hint`, `js.page_range_no_source`, `js.page_range_applied`, `js.page_range_none_copied`.

## New in 2.8.10 (carried forward, unchanged this release)

Fix release: dragging a signature box no longer locks itself against further dragging after its first autosave. 2.8.9 tied "locked against dragging" to the same `confirmed` flag used for sign-eligibility, and since the ordinary single-placement flow has always defaulted to confirmed automatically (for backward-compatible signing), its very first drag-triggered autosave froze the box against itself. `locked` is now a separate, purely human-driven flag, decoupled from `confirmed`, that only ever changes via the confirm checkbox itself. See "New in 2.8.10" further below for full detail.

## New in 2.8.10

- `db.py`: added `locked INTEGER NOT NULL DEFAULT 0` to `attendance_signature_placements`'s `CREATE TABLE` (fresh installs) plus an `_add_column_if_missing` call in `init_db()` (existing installs, including every database that already has the 2.8.9 `confirmed` column). Defaults to unlocked for every placement, old and new, confirmed or not.
- `main.py`: `_save_placement_row` now returns `(id, confirmed, locked)`. Repositioning by exact `placement_id` now also reads and preserves `locked`, and refuses (400) to move a row that is locked. The default upsert path (main/default placement, broadcast targets, apply-template, auto-detect, the per-page toggle grid) and the `new_instance=True` path both now explicitly return `locked=False` alongside their existing `confirmed` behavior (unchanged from 2.8.9) — neither ever sets `locked=True` on its own; only the confirm endpoint does.
- `main.py`: `POST /api/signing/placement/confirm` now sets **both** `confirmed` and `locked` together from the same boolean — checking the box means "reviewed, OK, don't touch it again" (confirmed AND locked); unchecking reverses both (freed to drag again, but also pulled back out of signing until reviewed and re-checked). Response now includes `locked` alongside `confirmed`. `/api/signing/placement`'s response also now includes `locked` for the row it just saved/created.
- `main.py`: `signing_sign()`'s gate is unchanged — it still checks only `confirmed`, not `locked`.
- `app.js`: split the single `activeConfirmed` state into `activeConfirmed` (sign-eligibility, used only for the "N unconfirmed" pre-sign count) and a new `activeLocked` (whether the active box can be dragged/resized/reset), each fed from `applyPlacement`/`savePlacement`/`toggleConfirm` off the matching server field. - `app.js`: `renderInstanceBoxes()` (the non-active per-page boxes) now derives its `.locked` class and checkbox-checked state from `isLocked(inst)` instead of `isConfirmed(inst)`, for the same reason. `toggleConfirm()` now updates both `confirmed` and `locked` together in the cached placement objects and in `activeConfirmed`/`activeLocked` when it's the active box. `savePlacement()`'s cached placement objects now also carry `locked` (from the server response for the current document; always `0` for broadcast targets, matching their unaffected `confirmed:1` default).
- No schema removed, no i18n keys changed, no HTML template changes — the toolbar markup and CSS `.locked` styling from 2.8.9 are unchanged; only which flag drives them changed.

## New in 2.8.8

- `db.py`: dropped `UNIQUE(attendance_id,signature_id,page)` from `attendance_signature_placements`'s `CREATE TABLE` — a page can now hold more than one placement for the same signature. Added `_migrate_placements_allow_multiple_per_page(con)`, run at the very start of `init_db()` (before `executescript(SCHEMA)`, which only creates tables that don't exist yet and would otherwise leave an existing constrained table untouched): detects the old constraint via `sqlite_master`'s stored SQL for the table, and if present, rebuilds the table without it (rename → create new → copy all rows with their original ids → drop the renamed original). A brand-new database never had the constraint and skips this entirely; running it again after migrating is a no-op (nothing left to detect).
- `main.py`: added `_save_placement_row(aid,sid,page_no,vals,uid,placement_id=None,new_instance=False)`, replacing three near-identical `INSERT ... ON CONFLICT(attendance_id,signature_id,page) DO UPDATE` statements (which relied on the now-removed unique index as their conflict target, so they no longer work) in `signing_placement` (both the primary save and each "apply to selected" broadcast target), and `apply_signature_template`. Default behavior (no `placement_id`, no `new_instance`) reproduces the exact old upsert-by-(attendance_id,signature_id,page) semantics via an explicit `SELECT ... ORDER BY id ASC LIMIT 1` then update-or-insert, so every caller that never needed to know about multiple instances (broadcast targets, apply-template, auto-detect) is unaffected. `placement_id` updates one exact row by id (validated to belong to the given document). `new_instance=True` always inserts a fresh row even if one already exists for that signature+page. `/api/signing/placement`'s response now includes `placement_id` (the id of the row the primary document's save touched or created).
- `main.py`: `/api/signing/placement/remove` now accepts an optional `placement_id` for deleting one exact instance; without it, falls back to the legacy `signature_id`+`page` addressing, which now deletes every row matching that pair (previously there could only ever be one).
- `app.js`: introduced `activePlacementId`, the id of whichever specific placement row the box is currently showing (`null` for an unsaved position — a suggestion, a reset, or a freshly started "add signature" instance). `applyPlacement(pl)` is the single place that keeps it in sync (set from `pl.id` when a real placement is applied, cleared to `null` for a suggested/blank box). `savePlacement()` sends `placement_id` whenever it's set (so dragging a specific instance always updates that exact row, never an ambiguous "first match") and captures the (possibly newly-created) id back from the response for the next save. `forceNewInstance` is set for exactly one save right after "+ Add signature" chooses a signature that already has a placement on the page, so that one save is forced to create a new row instead of reusing the existing one.

Clicking a chip applies that exact instance's saved position and switches the active signature to match, without dispatching `sigSel`'s `change` event (which would have re-resolved via "first match for this signature+page", picking the wrong instance when more than one exists). `pageSigAddBtn`'s click handler (and its picker) now always lists every registered signature via `addSignatureInstance(sid)`, which never filters by "already placed" and always starts a brand-new, not-yet-saved instance (offsetting the default box position slightly per existing instance on the page so a new one isn't invisible under another). `removeSignatureFromPage(placementId)` now takes a placement id instead of a signature id, for precise single-instance deletion; if the removed instance was the active one, falls back to another remaining instance of the same signature on this page if one exists, else shows the usual suggestion.
- `app.js`: the `confirmSignBtn`/`previewBtn` resave guard (added in 2.8.6 to stop a merely-suggested or just-removed position from being silently saved) now checks `activePlacementId` instead of re-deriving "does this signature have a placement here" via `placementFor()` — more precise once a signature can have multiple placements on one page, and correctly still refuses to save a freshly-added-but-never-dragged instance.
- `app.js`: `resetPosition`'s click handler no longer calls `applyPlacement(null)` (which would clear `activePlacementId`) — it moves the box back to the default visual position directly, preserving which saved instance (if any) is still active, so a drag afterwards updates that same instance rather than an unrelated one.
